## 2. 与设计一致（抽查记录）

- 验证策略：`smart` 的窗口由 `authenticate()` 成功即记录，金库端口 `expoAuthenticate` 走同一函数，所以签名验证也计入"最近验证过"；`always` 先 `lockKeys()` 再放行（`use-require-verification.ts`）。应用上锁 `forgetVerification()`（`useAppLock.lock`）。
- 启用流程：`useEnablePredict.done` 随 `onStep` 推进；`approvalsVerified` 先看凭证里的 `approvedSafe` 再读链，`enable()` 等到授权可见后写入。
- 资产：`composeOverview` 逐链；`wallet.chains` 只数这次拿到余额的链；未定价持仓与未返回的链都算"部分合计"，但 `loading` 期间不显示"部分合计"文案（避免每次打开都闪一下警告）。
- 盘口：`deriveBookView` 的 No 侧镜像、累计额、卖盘远→近排列均与网页版 `OutcomeOrderbook` 一致（单测 4 例）。
- 记录：平台索引到的取回以平台为准（`mergeFundRecords`），本机记录只补索引没追上的。
- 退出：首页两次返回（边缘滑动 / 返回键）2 秒窗口；iOS 不做。交互规范 §1 原文"首页再按走系统"被本需求覆盖。
- 平台契约 §3.7 各条（429 退避、40101 重签、CLOB 401 丢密钥、重装清凭证、SafeTx 串行、限流不重试）本轮未触碰，仍成立。

## 4. 遗留问题与设计方案

### 4.1 链上收款记录（设计 §3.3）

**现状**：App 只能列本机发出的转出；打到地址上的转账没有来源。

**方案（2026-09-06 详细设计，独立文档 `wallet-receive-index-2026-09-06.md`）**：RN-Server 仓库内新增独立进程 `./rn-server indexer`（同镜像、单实例租约），按链轮询平台单独配置的扫链端点：目录内 ERC-20 用 `eth_getLogs`（带代币合约 `address` 过滤 + 被监听地址 topic，≤1000 地址一组）双向索引；原生币入账用 Multicall3 余额差触发、只在增加时对本轮区间定界扫块，解释不了的增量记 `unattributed` 行而不是丢掉。落 `wallet_transfer_index` / `wallet_index_watch` / `wallet_index_cursor` 三张表，接口 `GET /v1/mobile/wallet/transfers` 复用 `Authorization: Wallet` 会话鉴权，返回 `indexedUpTo` 供 App 显示落后与"未开启索引"状态；推送前置是 `wallet_session` ↔ 安装的关联。实测约束（决定了设计）：BSC 默认端点完全不能 `eth_getLogs`，ETH 默认端点只能带合约地址且 ≤100 块，Monad 出块 0.3s 且 `eth_getLogs` ≤100 块；Etherscan V2 覆盖全部五条链但配额按用户 × 链轮询不可持续，只作为可选增强不进正式来源；App 端自扫在 Monad 上离线一天要 2880 次请求，否决。

### 4.2 主网 `unwrapDelay` 2 小时的"可领取"提醒（平台文档 §5.4）

**方案**：发起取回成功后，App 用 `expo-notifications` 排一个本地通知（`claimableAt`），点击深链 `anyfun://records?tab=predict`；同时把 `requestId + claimableAt` 交给 RN-Server（`POST /v1/mobile/reminders`）作为服务端推送的后备（设备关机 / 本地通知被清）。两条都是"事实驱动"的时间点，不猜延迟。

### 4.3 争议提交（平台有用户侧流程，此前判断有误）

**更正**：此前文档写"平台无入口"是错的（`predict-platform-integration-2026-09-02.md` §2.9 行 132 当时只 grep 了 `submitDispute`）。网页版 `ResolutionProgress.tsx` 的 `RaiseDisputeModal`（`apps/user-dapp/src/components/markets/ResolutionProgress.tsx:500-800`）实现了完整的用户争议流程，平台侧配套已齐：

| 事实 | 来源 |
|---|---|
| 证据意向接口 `POST {gamma}/disputes/evidence`，**无鉴权**，body `{conditionId, disputer, evidence, links}`，返回 `{evidenceId}` | `gamma-service/internal/handlers/router.go:137`、`handlers/dispute_evidence.go` |
| 校验：证据 150–1000 个字符（按 rune）、链接 ≤5 条、必须 `https://` 且 ≤500 字符、`disputer` 为 0x 地址；条件必须处于 `proposed`（否则 `requested/open` → 409 `not open`，已争议/结算 → 409 `already exists`）；未知条件 404 | `gamma-service/internal/service/dispute_evidence.go:15-110` |
| 证据行 `pending` → tenant-service 的 oracle indexer 看到 `PriceDisputed` 后按 `(conditionId, disputer, round)` 关联为 `committed`；24h 未上链转 `expired` | `tenant-service/internal/worker/oracle_indexer.go:779-791`、`config.go:341/473`、`scripts/schema.sql:1817-1832` |

**App 设计**（对齐网页，走 EOA 付 gas，复用转入的合约调用原语 `OnchainTransfers.callContract / readContract`，`http-predict-account-gateway.ts:815`）：

1. **数据**：`gammaAdjudicationSchema`（`core/predict-platform/gamma.ts:72-83`）加 `adapterInstance / ancillaryData / requestTimestamp / questionId / nextSteps`；`platformContracts`（`public-info.ts:120-152`）加 `umaAdapter / negRiskUmaAdapter / sportsOracle`（按需 `need()`，缺则 `PredictPlatformContractMissingError`）。`Adjudication` 模型加 `phase`（平台 `currentPhase` 原值）、`adapter`、`disputeKey {requester, identifier, requestTimestamp, ancillaryData}`；`canDispute = phase === "liveness_period" && adapter !== "crypto_periodic"`，以平台算好的 phase 为准，不再自己从字段推。
2. **争议条款读取** `getDisputeTerms(marketId)`：`adapter.optimisticOracle()` → `LightOracle.getRequest(...)` → `{bond: Money(USDW), expiresAt, oracle}`，加上 EOA 的 USDW 余额与 native 余额；面板打开时读，倒计时以链上 `expirationTime` 为准（网页同样不用 `livenessDeadline`）。
3. **提交** `submitDispute(address, marketId, {evidence, links}, signer, onStep)` 四步，每步进 `onStep` 供面板显示：`evidence`（POST gamma，带租户头；400/404/409 映射为带文案 key 的 `PredictDisputeError`）→ `bond`（EOA USDW < bond 时抛 `PredictInsufficientBondError`；面板提供"用钱包 USDC 兑换 USDW 到本地址"一键操作 = `wrapper.wrap(USDC, bond, EOA)`，复用 `depositCalls` 但 `to = EOA`）→ `approve`（allowance < bond 时）→ `dispute`（广播前用 `Date.now()` 再核一次 `expiresAt`；回执 `status=0` 按失败）。签名前走 `useRequireVerification`（smart / always 策略同下单）。成功后把 `challenger = 本地址` 写进 `predict-adjudication` 查询缓存作乐观态，直到 gamma 返回 `challenger`。
4. **界面**（`settlement-screen.tsx:340-370` 的单行"争议理由"面板替换）：多行证据输入 + 150/1000 计数、最多 5 个 `https://` 链接（客户端校验与服务端常量一致）、押金行（押金 / 本地址 USDW 余额 / 不足提示 + 兑换按钮）、到期倒计时、四步进度、`crypto_periodic` 市场不显示争议步骤、已争议后按钮变"已提出争议 · 等待仲裁"。错误文案：`LivenessAlreadyExpired` → "争议窗口已关闭"，409 → "本轮已有争议"。
5. **测试**：网关步骤序列（allowance 充足 / 不足、到期、证据 4xx）用假 onchain；面板计数与链接校验；dev 端到端需要一个 `regular / neg_risk / sports` 市场处于 `proposed`——和 §4.4 一样要请平台方在 22 个 regular dev 市场里提案一个（或建短 liveness 测试市场）。
6. **平台侧记录（转 §5）**：证据接口无鉴权（任何人可替任意地址登记意向；只在链上匹配时提交，可接受但要知道）；押金用 USDW 而用户的 USDW 在 Safe 里、争议却必须从 EOA 发——若平台愿意把 LightOracle 加进 relayer 白名单，App 可改走 Safe 免 gas 且不用兑换；`adjudication` 不带 `bond`，客户端必须读链。

### 4.4 领取（redeem）未在真实结算市场验证

dev 上没有会结算的市场。方案：请平台在 prax1s 建一个 5 分钟到期、自动结算的测试市场（`recurring` 系列即可），验证 `redeemPositions` 的 MultiSend 与 `/positions` 的 `redeemable` 判定后再开放主网领取入口。

### 4.5 iOS 未验证

无 macOS 构建环境。至少要在 EAS 上出一次 iOS dev build 验：锁屏面容图标、`GestureDetector` 与原生 stack 手势的共存（二级页边缘返回由 native-stack 处理，AppShell 的边缘手势只在标签页）、`BackHandler.exitApp` 分支已按平台跳过。

### 4.6 偏好存储小清理

`appLockMethod` 字段无读取方；`largeAmountThresholdUsd` / `autoLockMinutes` 用"点一下循环切换"的交互（安全中心 `cycleLock` / `cycleThreshold`）不符合交互规范 §2 的"选择器"要求。方案：偏好存储升 v3 删除 `appLockMethod`；两个数值改为 `RadioRow` 面板（复用 `TxVerificationSheet` 的形态）。

### 4.7 多结果事件的多线走势

已实现（`usePriceHistories` + 图例），模拟器上对 dev 的"inflation"多结果事件核过一次；线的颜色取自主题 token（涨跌色 / info / warning / muted），超过 4 条只画概率最高的 4 条，与网页版 `MAX_VISIBLE_HISTORY_LINES` 相同。
