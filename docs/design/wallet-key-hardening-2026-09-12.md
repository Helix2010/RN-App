## 0. 一页纸

| 编号 | 决策 | 一句话理由 |
| --- | --- | --- |
| D1 | bootstrap 响应用 secp256k1 签名，不用 RSA | 两端都已有审计过的实现，零新依赖 |
| D2 | 金库条目拆分：账户私钥与助记词分开保管 | 今天每次签名都要解出助记词并重新派生 |
| D3 | 助记词那一层额外加一道用户口令 | 把"静默导出助记词"变成"必须骗到口令" |
| D4 | 包裹密钥启用 `requireAuthentication`，**同时**保留一份口令封装 | 单份保管必然产生永久丢钱的悬崖，两份就没有 |
| D5 | 新建钱包默认 24 词，界面允许用户选 12 | 默认给强的，需要好抄的人自己降级 |
| D6 | **不**把派生搬到原生 | 见 §6.1 |
| D7 | **不**支持 BIP-39 passphrase | 见 §6.2 |
| D8 | **不**让认证绑定的密钥成为包裹密钥的唯一副本 | 见 §6.3，这是 D4 最容易做错的地方 |

实现顺序：§2 → §3 → §4。§2 与另外两节没有耦合，可以并行，但它没有存储改动、没有 UI 改动、失败了也不会弄坏任何人的钱包，应该先做完拿到一次干净的上线。

## 2. N3：bootstrap 响应签名

### 2.1 算法选择

用 secp256k1，不用 RSA，也不用 Ed25519。理由是两端的实现都已经在手上，且都不是新引入的信任：

| 位置 | 现成的东西 | 今天已经在用它做什么 |
| --- | --- | --- |
| 服务端签名 | `github.com/decred/dcrd/dcrec/secp256k1/v4` 及其 `ecdsa` 子包，go.mod 里的直接依赖 | `internal/siwe/siwe.go` 验证 EIP-4361 登录签名 |
| App 验签 | ethers 的 `verifyMessage` | 用户资金的全部签名 |

也就是说，验 bootstrap 用的是这个钱包**已经拿用户资金在信任**的那份密码学实现。往 JS 里塞一个 RSA 验证器，或者为了 Ed25519 引一个新的曲线库，都会在最敏感的位置增加一份没人审过的代码。

### 2.2 签名范围与编码

沿用 EIP-191 personal_sign 信封，这样两端各自只有几行：

```
服务端：digest = keccak256("\x19Ethereum Signed Message:\n" + len(body) + body)
        sig    = ecdsa.SignCompact(key, digest, true)   // 返回 [V+27 || R || S]
        重排为 [R || S || V] 后 hex 编码
App：   ethers.verifyMessage(bodyBytes, sigHex) === 钉住的签名者地址
```

两个必须做对的地方。

**一、签的是发出去的那串字节本身。** 现在 `(*server).bootstrap`（`internal/api/server.go:1443`）构造一个 `gin.H` 然后交给 `c.JSON` 序列化。改成先 `json.Marshal` 一次拿到 `body`，签这个 `body`，再把同一个 `body` 原样写进响应。任何"签完再序列化一次"的写法都会在某天因为一个字段顺序或一个转义差异而炸掉——OTA 验签那次已经踩过一模一样的坑。

**二、字节序要重排。** dcrd 的紧凑编码把恢复位放在**最前面**并加 27，ethers 要的是恢复位在**最后**。`siwe.go` 的 `RecoverAddress` 里已经有这段注释和这段代码，照抄反向即可。这是最容易丢一天的地方。

`personalHash` 目前只接受 `string`，需要一个接受 `[]byte` 的变体。长度前缀数的是**字节**不是字符，这一点现有实现已经注意到了。

签名放 HTTP 响应头，不放 JSON 字段内部：客户端可以在解析之前先验证它收到的原始字节，不需要任何规范化约定。头的形状沿用 OTA 那套 RFC 8941 字典（`sig`、`keyid`、`alg`），保持一致；`alg` 用我们自己的取值，因为这不是 expo 的通道。

### 2.3 防重放

签名本身不解决重放。能做中间人的人可以把昨天那份**合法签名**的 bootstrap 重新发一遍，把更新策略、灰度名单或者链配置回滚到旧值。

载荷里加一个单调递增的序号，客户端记住见过的最大值，拒绝比它小的。这与 `contract-pin.ts` 的 TOFU 是同一个形状，也应当同样 **fail closed**：序号变小就拒绝启用新配置并保留旧的，而不是"取不到就放行"。

序号的世代常量与合约钉住的 `CONTRACT_PIN_EPOCH` 一样，改它需要发一次原生版或 OTA，全体设备重新记一次。

### 2.4 分两个版本上线

这条**天然跨两个版本**，不要试图一次做完：

| 步骤 | 服务端 | App | 期间的存量设备 |
| --- | --- | --- | --- |
| 1 | 开始签，头里带签名 | 不变 | 正常，忽略未知响应头 |
| 2 | 不变 | 有签名就验，验不过拒绝；没有签名照旧接受 | 正常 |
| 3 | 不变 | 没有签名也拒绝 | 只有跑到步骤 2 之后版本的设备才生效 |

跳过步骤 2 直接强制，会把所有还没升级的设备锁在门外。这与打包代理"先服务端后代理"的升级顺序是同一类约束。

### 2.5 密钥保管

签名私钥与 OTA 签名私钥**分开**：共用一把等于把两个信任域焊在一起，任何一边的泄露都同时毁掉另一边。它跟 OTA 签名密钥一样按租户隔离、存在服务端、绝不进打包机。

签名者地址是一个 20 字节常量，编进 tenant 配置随包发布。它不是秘密，可以随便打印和比对。

### 2.6 影响面

| 仓库 | 文件 | 改动 |
| --- | --- | --- |
| RN-Server | `internal/siwe/siwe.go` | 增加接受 `[]byte` 的 personal hash 变体 |
| RN-Server | `internal/api/server.go` | `bootstrap` 改为先 marshal 再签再原样写出；加序号字段 |
| RN-Server | 新增签名密钥的存储与管理端入口 | 复用 OTA 签名密钥那套按租户加密存储 |
| RN-App | `src/core/config/bootstrap-repository.ts` | 验签、比对钉住地址、检查序号 |
| RN-App | tenant 配置 | 新增签名者地址常量 |

验收：改一个字节的响应体，验签必须失败；重放一份序号更小的合法响应，必须被拒绝；步骤 2 的版本在服务端不带签名时必须仍能启动。

## 3. N6 与 N29：金库重构

### 3.1 先说清楚威胁模型变了

OTA 代码签名上线之后，"恶意 JS 进入 App 进程"的投递路径只剩两条：构建期被投毒的依赖，以及运行时的 JS 层 RCE。恶意 OTA 包这条路已经被嵌入证书堵上了。

这不意味着 N6 可以放着。这类攻击者拿到的东西差别极大：

- 拿到助记词 = 全部未来资金、全部链、全部派生账户、永久有效、可离线使用。
- 拿到一次签名机会 = 只有当时那几个账户里的钱。

所以这次重构的目标不是"挡住有代码执行的攻击者"（在 JS 里这做不到），而是**把静默的、一次性的、永久的窃取，降级为必须与用户交互的窃取**。交互是有声音的、会失败的、用户看得见的。

### 3.2 今天的形状

已核实：条目里存的就是助记词本身，`withPrivateKey` 解密后调 `assertOwner` 重新派生出私钥。一次签名 = 一次助记词解密 + 一次根种子派生。

```
条目 = { address, kind: "mnemonic" | "private-key", path, salt, nonce, ciphertext }
密文 = AES-256-GCM(助记词或私钥)，key = HKDF-SHA256(WK, salt)
WK   = SecureStore 里的一条，读它不需要任何系统验证
```

### 3.3 新的形状

条目按用途分成两类：

```
accounts[]  密文 = 派生出来的那一把私钥
            key  = HKDF-SHA256(WK, salt)

seeds[]     密文 = 助记词
            key  = HKDF-SHA256(WK ‖ scrypt(口令), salt)
```

账户条目记 `seedId` 与 `path` 说明自己从哪来；导入的私钥没有 `seedId`。

这一个改动同时解决两件事：

- **N29 第三部分**：日常签名只解一把账户私钥，根种子再也不进堆。不需要原生模块。
- **N6 残留**：想拿助记词必须同时有 WK 和口令；拿到 WK 只能拿到已经存在的那几把私钥，拿不到派生未来账户的能力。

GCM 的 AAD 继续按现有做法把条目元数据绑进认证标签，`seedId` 一并纳入。

### 3.4 各操作需要什么

| 操作 | WK | 口令 | 系统验证 | 根种子进堆 |
| --- | --- | --- | --- | --- |
| 列出账户 | 否 | 否 | 否 | 否 |
| 签名 | 是 | 否 | 读 WK 时一次 | 否 |
| 导入私钥 | 是 | 否 | 是 | 否 |
| 查看助记词 | 是 | 是 | 是 | 是 |
| 新增派生账户 | 是 | 是 | 是 | 是 |
| 创建钱包 | 是 | 是 | 是 | 是 |

"新增派生账户需要口令"是有意的：它和"查看助记词"一样需要根种子，而它是低频操作，这点摩擦换得起。

### 3.5 包裹密钥的两份封装

这是 D4 的核心，也是唯一一处做错就会让用户永久丢钱的地方。

**同一把 WK 保存两份，互相独立：**

```
A 路  SecureStore 条目，requireAuthentication: true
      快路径。读它会弹系统验证，JS 伪造不了也绕不开。
      操作系统可以在任何时候作废它。

B 路  AES-256-GCM( AES-256-GCM(WK, key=scrypt(口令)), key=未认证的 SecureStore 密钥 )
      恢复路径。永不被作废。设备没录入生物识别时它是唯一的路径。
```

不变量：**任何铸造或轮换 WK 的操作必须同时写两份**，两份永远是同一把。

读取顺序：先试 A。A 报"密钥已失效"或"不可用"时，提示用户输入口令走 B，成功后立刻重建 A。

前置条件：**没设口令的用户不开 A。** 由此这条路上不存在悬崖——A 被作废时 B 必然存在。

**为什么必须有 B（D8）：** 已核实 `expo-secure-store` 57 的实现，两个平台都会作废这把密钥。

| 平台 | 代码 | 作废条件 |
| --- | --- | --- |
| Android | `AESEncryptor.kt` 调 `setUserAuthenticationRequired(true)`，**没有**调 `setInvalidatedByBiometricEnrollment(false)`，而该项默认为 true | 新录入指纹；移除锁屏 |
| iOS | `SecureStoreModule.swift` 用 `.biometryCurrentSet` | 生物识别集合发生变化 |

也就是说，用户去派出所按了个新指纹、或者换了个手势锁，这把密钥就没了。如果它是 WK 的唯一副本，那一刻这个钱包就永久打不开了，而绝大多数用户不会在那之前认真抄下助记词。这不是小概率事件，是**必然会发生在一部分用户身上**的事件。

Android 上 expo 给认证条目和非认证条目用的是**两个不同的 keystore 别名**（`:authenticated` / `:unauthenticated`），所以给一条已有条目"打开 requireAuthentication"实际上是换了一把密钥，旧值读不出来。开启流程必须是"从 B 读出 WK，再写进 A"，不能指望原地升级。

**B 为什么要双层封装：** 内层口令派生的密钥防的是拿到 JS 执行权的攻击者，外层未认证的 SecureStore 密钥防的是另一类人——把 AsyncStorage 整个捞走的人，包括 adb 备份、云备份、以及某天不小心把存储打进日志。单独一份 B 的密文离开这台设备之后毫无用处。这与服务端 keystore 的双层封装是同一个思路：内层是操作者口令，外层是服务端主密钥。

**诚实的边界：** B 存在，就意味着骗到口令的攻击者能拿到 WK。A 的价值不在于抬高天花板，而在于**取消静默这个选项**：没骗到口令的攻击者，什么都拿不到，而且他的每一次尝试都会在用户屏幕上弹出一个系统验证框。口令的职责是让窃取变成交互式的，不是让它扛住离线爆破。所以不要为口令强度设计苛刻的规则，8 位加一个强度提示就够了，把复杂度花在别处。

**两个 UX 事实**，实现时会撞上：

- 读 requireAuthentication 的条目会**阻塞 JS 线程**，expo 的文档明确写了。所以读 WK 必须发生在一个受控的时机，比如显式的解锁动作，不能在渲染过程中懒加载。现有的 5 分钟 WK 缓存正好配套：用户每 5 分钟见一次系统验证框，这正是钱包应有的样子。
- `SecureStore.canUseBiometricAuthentication()` 会在设备没录入时返回 false。这类设备只能走 B，要当成正常状态处理，不能报错也不能把用户拦在外面。

### 3.6 口令

- 派生用 scrypt，`@noble/hashes` 里已有，不引新依赖。参数**要在目标低端机上实测再定**，起点 N=2^15、r=8、p=1，如果 p50 设备能压在一秒半以内再往上抬。服务端 keystore 用的是 2^16，手机上纯 JS 跑不动同样的参数，不要照抄。
- 存一个校验值：`HKDF(scrypt(口令), "check")` 的前几个字节。这样口令输错时报"口令不对"，而不是报一个 GCM 认证失败。
- 这一点与服务端 keystore 的做法**相反**，那边故意让"口令错"和"内容坏"返回同一个错误以免形成判决神谕。这里威胁模型不同：用户必须知道自己是打错了字还是数据坏了，而攻击者本来就能自己试。这个差异是有意的，不要"统一"掉。

### 3.7 存量升级

按决定不为迁移做额外设计，但也不能弄坏现有钱包，所以取最简单的一条：

- 现有条目在首次解锁时就地升级为账户条目，密钥仍是 WK 单层。
- seed 条目在用户设置口令之后才建立；在那之前，助记词维持今天的 WK 单层加密。
- 因此 A 路也在用户设置口令之后才开启。

沿用现有的损坏归档纪律：任何会替换原文件的写入之前，先把原始内容归档到 `foundation.wallet.vault.v1.corrupt.<ISO 时间>`。

## 4. N29：默认 24 词，界面可选

新建钱包默认 256 位熵，界面上给用户一个 12 / 24 的选择。默认给强的那个，需要好抄的人自己降级——这比默认给弱的、指望用户去高级设置里找强的要好。

导入路径不受影响，本来就两种都收（`wallet.import.mnemonicPlaceholder` 的文案已经写着"12 或 24"）。

### 影响面

| 文件 | 改动 |

## 6. 明确否决的三件事

这三条都看起来像"更安全"。写下理由是为了不被重新提出。

### 6.1 不把派生搬到原生

能读 JS 堆的攻击者同样能直接调用签名函数。把根种子挪出 JS 并没有拿掉他的能力，只拿掉了一件他不太需要的东西——他要的是签名结果，不是种子本身。为此维护一套分平台的原生模块、破坏 Expo 的工作流、给打包链路再加一个环节，换来的边际防护接近零。

§3.3 的条目拆分已经顺手把根种子请出了签名路径，代价是零。

### 6.2 不支持 BIP-39 passphrase

它的失败方式是**静默的**：口令打错不会报错，只会打开另一个合法但空的钱包。用户就是这样丢钱的，而且丢了之后没有任何提示告诉他发生了什么。

如果一定要有第二道口令，它应该加在我们自己的加密层上，也就是 §3.6——同样的 UX，但输错时会明确报"口令不对"。同时上这两样只会让用户分不清自己在输哪一个。

### 6.3 不让认证绑定的密钥成为唯一副本

见 §3.5 的作废条件表。两个平台的 `expo-secure-store` 实现都会在用户改锁屏或重录生物识别时作废这把密钥。作为唯一副本，它等于给每个用户装了一枚随时可能触发的、会永久销毁钱包的开关。

`requireAuthentication` 本身要开，D4 已经确认。必须和 §3.5 的 B 路一起开。
