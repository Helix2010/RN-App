# Fix: 安装包下载到 100% 之后要等好几秒才出安装界面

状态：Implemented（`pnpm check` 全绿；模拟器上核对了新阶段的文案与按钮）

## 现象

用户反馈：App 检测到新版本、选择下载，进度条到 100% 之后「隔了好一会」才到安装界面。

## 原因

100% 与安装界面之间只有一件耗时的事：**整包 SHA-256 校验**（安全评审 N2：安装前
必须与 bootstrap 下发的摘要一致）。而这一步跑的时候，状态机**还停在
`phase: "downloading"`**，进度是 100%——界面上就是一个不动的满进度条。

时序（`apk-download-manager.ts` 的 `run()`）：

1. 最后一次进度回调把 written 推到 total，界面显示 100%；
   （实际还要早一点：百分比是 `Math.round`，99.5% 就显示 100%）
2. 下载 promise resolve，`clearStallTimer()`，查一下文件大小——都是瞬时的；
3. **`digestOk()` → `hashFileSha256()`**，整包读一遍算摘要；
4. 算完才 `setState({ phase: "ready" })`，弹层这时才把「安装」送到眼前；
5. 安装器**不会自动打开**，要用户再点一下「安装」。

第 3 步的开销来自它的实现方式：按 1 MiB 分片，每片
`FileSystem.readAsStringAsync(..., Base64)` 跨一次桥，返回一个 1.33 MB 的 base64
字符串，再 `atob()` 出一个 1 MiB 的字符串，再用 `charCodeAt` 逐字节循环填进
`Uint8Array`，最后交给纯 JS 的 SHA-256。一个 39 MB 的包就是 **39 次跨桥往返、
约 52 MB 的 base64 字符串要搬运并在 JS 堆上分配、约 4100 万次 `charCodeAt`**。

纯 JS 那部分在桌面 V8 上实测 212 ms（atob + 循环 75 ms、SHA-256 137 ms；
同样数据用原生 crypto 只要 18 ms，差 12 倍）。手机 Hermes 比桌面 V8 慢数倍，
再加上跨桥与 GC 压力，几秒是预期之内的。

**排除掉的两个怀疑**：stall 定时器不会误判（`clearStallTimer()` 在 `task.start()`
的 `finally` 里、算摘要之前）；`start()` 在校验期间也不会再开一轮下载。

## 改动

1. **新增 `verifying` 阶段**。下载完成后先切到它再算摘要，界面因此能说
   「正在校验安装包，马上就好…」而不是顶着一个 100% 的死进度条。
   这是本次反馈的直接成因——**不是把校验做快，而是别让它看起来像卡死**。
2. 四个消费状态的地方都补上这一分支，否则会静默落错：弹层主按钮原本会显示
   「立即更新」、状态行空白、进度条整条消失、关于页按钮显示「安装」（而文件还没
   校验完）。校验期间主按钮置灰，这一步没有可操作的东西。
3. `start()` 显式拦住 `verifying`。原先靠 `this.running` 非空间接挡住，
   那是依赖另一个字段的时序。
4. **分片从 1 MiB 调到 4 MiB**，跨桥次数从 39 降到 10，单次瞬时占用约 13 MB
   仍然有界。常量导出，测试从它派生，以后再调不会让「跨分片」的用例失效。

## 没有做的

**没有把摘要计算换成原生实现。** `expo-crypto` 只能对字符串算摘要，没有文件或流的
接口；`expo-file-system` 的新 `File` API 有 `readableStream()`（能直接吐原始字节，
省掉 base64、`atob` 与逐字节循环），但本仓没有流 polyfill，也没有任何现存用法，
在 release 包里未验证——而这条是安装前的完整性校验，安全关键，不适合凭推断改。
真要做，应该单独一件事：先在模拟器与真机上验证 `readableStream()` 可用，再换。

## 验证

- `pnpm check` 全绿。
- 新增用例：下载完到就绪之间必须经过 `verifying`，且这期间点「立即更新」不会再开
  一轮下载（用一个可控的摘要闸门把状态悬在中间来断言）。
- 分片用例改为从 `HASH_CHUNK_BYTES` 派生尺寸，仍然覆盖「两个整片 + 不足一片的尾巴」。
